## 2. Findings, ranked by how badly they would derail the plan

### F1 — W2 has no slot, three "funders", a circular wait with EP-MCP, and R3 depends on it
**Items:** W2 (US-MCP-00), EP-MCP (FD-8), S14-lite, S15–S18. **Type:** contradiction + complication.
**Evidence.**
- `roadmap.md:114-115`: "**Funded by** EP-MCP (FD-8), S14's adaptive half (it needs engine events) or crossfade. **Triggered by** any wrong-song or silent-playing bug".
- `roadmap.md:182`: "Placement (FD-8…): after W2 — one owner for playback — and the command layer, in R2 or later"; `backlog.md:1995`: "Funded by EP-MCP (FD-8)". So MCP waits for W2, and W2 is paid for by MCP.
- Size vs. the rule: `stage5-architect.md:335`: W2 "L / high (time-boxed per event family)"; `:311`: "A 2-week cap per slice … A strangler is never left with two live owners". A reducer that owns play/pause this fortnight and seek/advance next fortnight is two live owners of the transport in between.
- R3 needs it but the rows don't say so: `stage5-architect.md:427`: "**S15–S18** | W2 events; the W5 stage concept; per-track analysis at the seam"; `sprint-plan.md:110-113` list only "DSP spine", "S15", "S14, S16", "DSP spine; SPIKE-BRIR".
- Code today: no event channel exists. `AudioPlaybackEngine.swift:103`: "Gapless / continuous playback (poll-based — the view model reads a snapshot at 20 Hz)"; `AudioViewModel+TransportTick.swift:10-16`. Council C-06 (`stage5-architect.md:54`): "There is no event channel."
**Why it matters.** R3 is scheduled on a slice nobody is scheduled to build; the two things that could build it (EP-MCP, S14-adaptive) are themselves unscheduled or waiting on it; and its size cannot fit the cap the plan applies to every slice. The pre-mortem's own warning (`stage5-architect.md §4.7`: "W2 is never funded, and the RC-1 class persists") is still open.
**Severity:** must resolve before S14-lite (its row cites W2) and before S15.
**Recommended resolution:** give W2 a named slot and a size: ENG delivers the engine half (`roadmap.md:116` already says so); make "the queue/transport reducer + command layer" the slice that **S15** (the first R3 sprint) carries, since S15–S18 are the scheduled consumers; drop "S14's adaptive half" from the funders (see F2) and keep EP-MCP as a consumer, not a funder.
**Alternatives:** (a) make EP-MCP an R2 sprint of its own that begins with W2 (then MCP is R2 scope, which FD-8 allows); (b) state that S15–S18 need only "a seam event that carries the track's identity" (which ENG delivers) and strike "W2 events" from §4.6.

### F2 — S14-lite's dependencies are wrong in both directions: "Depends on: ENG" has no reason, "waits for W2" isn't needed, and its level input is blind to the volume keys
**Items:** S14-lite (US-TON-03, US-ADAPT-03), ENG, W2. **Type:** contradiction + complication.
**Evidence.**
- `sprint-plan.md:84`: S14-lite "| S7, loudness infra (have), ENG |". `roadmap.md:96`: "S14's adaptive half (the system volume observed, engine events) waits for W2". `stage5-architect.md:426`: "S14-adaptive needs the Enhanced system volume observed (DeviceIO) plus W2 events".
- S14-lite's code lives in the effects AU's Realizer (`Realizer.mm:397-418`, `realizeEq`), which ENG leaves alone: `backlog.md:1950` "our two audio units are unchanged".
- The "system volume observed" already has a mechanism, and it is not an engine event: `AudioEngineBridge+MasterGain.swift:150` `AudioObjectAddPropertyListenerBlock(device, &address, deviceVolumeQueue, block)` — a HAL volume listener on `deviceVolumeQueue`. Today it feeds Pure only: `:172-175` `masterGainOnPure.deviceChanged(…)`, `:177-178` "only while the path is Pure, so a late listener call after teardown can't paint a device volume onto Enhanced".
- On Enhanced, Master Gain is the player's volume (`+MasterGain.swift:44-46` `playerNode?.volume = MasterGainLaw.linearGain(…)`) and the device's own volume is never read. `backlog.md:663` (US-ADAPT-03): "Volume is monitored via system volume API (kAudioHardwareServiceDeviceProperty_VirtualMainVolume) and the in-app volume control."
**Why it matters.** (1) If ENG overruns — the council's own pre-mortem pattern — R2's first feature waits for nothing it uses. (2) Without the device volume, S14-lite compensates against an in-app slider most listeners never touch; the volume keys change the real level and the compensation stays put: "the loudness button" that doesn't follow the volume. (3) The circularity in F1 exists only because "engine events" was written where "a HAL volume listener" was meant.
**Severity:** must resolve before S14-lite (it defines what S14-lite ships).
**Recommended resolution:** decouple S14-lite from ENG and W2; its level input = Master Gain + the Enhanced device's volume from the existing listener (lifted out of the Pure-only gate), published to the Realizer the way `setOutputTransport` is (`Realizer.h:146`); "engine events" leave S14 entirely.
**Alternatives:** (a) ship S14-lite as "Master Gain only" and say so in US-TON-03 (then say what happens when the user uses the volume keys); (b) run S14-lite before ENG — nothing it touches is in ENG's scope.

### F3 — Gain and headroom have no summing owner; "respect the ±12 dB trust clamp" names a clamp that exists only per EQ point
**Items:** S14-lite (W5-min), R1.1-B leveling (US-R1F-10), S13 correction, S17, EP-MCP (US-MCP-05), architecture §11. **Type:** contradiction.
**Evidence.**
- `roadmap.md:96`: "Compensation must respect the ±12 dB trust clamp, with its own headroom or a cap"; `stage5-architect.md:277`: "taste ±12 plus compensation must respect the ±12 dB trust clamp (`Realizer.h:121-124`)".
- What that line of code is: `Realizer.h:120-123`: "The trust boundary … a NULL pointer, a wrong count or any non-finite point is rejected … finite points are clamped to ±12 dB" — an input guard per point (`Realizer.mm:209`; `EQBands.swift:26` `pointLimitDb: Float = 12`). It sums nothing.
- The other gain owners, each with its own clamp: −ΔL ±12 (`TrackLoudnessGain.cpp:14,120`); the AGC makeup −20…+12 (`LoudnessModule.h:55-56`); Master Gain "Turn-down only" (`MasterGainLaw.swift:5`); the limiter is a true-peak ceiling only (`LimiterModule.h:3-8`; `AudioConstants.h:16-21`); crossfeed "can add level" (`DSPKernel.cpp:321-324`). Compensation adds "+12 dB default" (`backlog.md:561`).
- The summing owner is design, scheduled S15–S16: `architecture.md:346-348`: "Hearing-Safety Numeric Clamps (DESIGN — NOT YET SHIPPED)… The clamp engine and the Arbiter that would enforce these do **not** exist"; `:358`: "Cumulative gain-driven loudness change | +12 dB | Hard". And `:348`: "The old summed-dB `EQSafetyClamp` was retired in Sprint EQ".
- A third would-be owner: `backlog.md:2001` (US-MCP-05): "Hearing-safety clamps server-side".
- EQ Off today = the flat design (`Realizer.mm:399-401`): with a compensation layer in the same contract, what "Off" and the bit-perfect badge (`DSPKernel.cpp:210-211` `isIdentity()`) mean is undefined.
**Why it matters.** In R2, taste (+12) + compensation (+12) + leveling can stack to +24 dB and more at 60 Hz ahead of a true-peak limiter, which will then do exactly what C-38 complained of ("+12 dB of makeup feeding a −1 dBTP limiter is DRC by default", `stage5-architect.md:108`). The clamp the row leans on cannot catch it, and the thing that could is two releases away.
**Severity:** must resolve before S14-lite (and inform R1.1-B's leveling cap).
**Recommended resolution:** S14-lite's slice includes the summing rule in the Realizer — per band, taste + compensation (+ correction later) ≤ 12 dB with proportional scaling (architecture §11 rule 3 in miniature) — and the roadmap row says "the Realizer sums and clamps the layers", not "respect the clamp". Define "EQ Off" and the bit-perfect badge per layer in the same change.
**Alternatives:** (a) a smaller compensation budget (+6 dB) until S16's Arbiter; (b) make the per-band cumulative clamp S14-lite's structural slice instead of "taste-only neutrality" (see F8).

### F6 — "A ceiling after the spatial stage" means two true-peak limiters in series, and crossfeed (and the effects-AU BRIR) run before the fold, so a 5.1 file on headphones gets no crossfeed
**Items:** R1.1-B #1 (C-43), S18, crossfeed (R1.1-A, C-42). **Type:** complication.
**Evidence.**
- `roadmap.md:62` "a safety ceiling after the spatial stage"; C-43 (`stage5-architect.md:113`): "The limiter sits before the spatial AU, so any fold-down breaks the ceiling."
- The limiter is the effects AU's last stage (`DSPKernel.cpp:325-331` `renderOutput`: crossfeed, then limiter; `LimiterModule.h:3-8` "Final stage of the signal chain"), with a 3 ms look-ahead (`AudioConstants.h:30`). The spatial AU has no limiter (its includes, `SpatialRenderKernel.cpp:1-5`) and no parameter plane to receive a ceiling (`AudioUnitRegistrationBridge.h:43-52`).
- Crossfeed is stereo-only and bypassed at any other width: `CrossfeedModule.h:37` "Stereo only: any other width"; `:62-65` `isBypassed(params, channels)`. The effects AU runs at the source width N (`AudioEngineBridge+Graph.swift:64-66`), so on a 5.1 file crossfeed is bypassed, and the fold's stereo output never passes it.
**Why it matters.** Either a second limiter runs after the fold (two ceilings in series on the M<N case, 6 ms look-ahead, the first one having already limited each of six channels) or the one limiter moves — and the effects AU cannot know M to skip itself. A headphone listener with crossfeed on hears a folded 5.1 album without it, and no story says so.
**Severity:** should resolve before R1.1-B (fold into F5's design).
**Recommended resolution:** decide in R1.1-B's design whether the output stages (crossfeed, limiter) move after the fold — which is C-47's minimal form, in the sprint that needs it — and write into US-R1F-08 what crossfeed does on a folded file.
**Alternatives:** (a) accept two limiters as the interim and document the latency and the double-limiting; (b) fold inside the effects kernel (F5 alt a), which puts crossfeed and the limiter after the fold for free.
