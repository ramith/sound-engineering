## 2. Findings, ranked by harm to what the listener hears

### F1 — Leveling (R1.1-B) and Pure mode: our story is silent, and the device-volume loan will misread a leveling move as the listener's
- **Our items:** R1.1-B #7 / US-R1F-10 (Leveling Off/Album/Track), Pure mode, "Master Gain drives device volume in Pure" (R1.1-A).
- **Type:** complication (and a gap).
- **Evidence — ours:** US-R1F-10's acceptance says only "Off changes nothing: the bit-exact anchor holds" (`docs/product/backlog.md:1752-1763`) — nothing about Pure (docs only — not in code). In code, Pure never scales the stream and the only gain is the device loan (`MasterGainOnPure.swift:1-13`); the loan treats any device reading that differs from what Pure last set as **the listener's own change** and re-anchors (`MasterGainOnPure.swift:312-329`).
- **Evidence — theirs:** MPD: "ReplayGain is usually implemented with a software volume filter (which prevents Bit-perfect playback). To use a hardware mixer, set `replay_gain_handler` to `mixer`" — and its filter then calls `mixer->LockSetVolume(_volume)` and returns the PCM untouched (`ReplayGainFilterPlugin.cxx:136-199`). JRiver: "Internal Volume does not work when bitstreaming" (Volume wiki). Audirvana: the internal volume "will replace the output device volume control" and "the two attenuations are cumulative" (help article). Roon: "MUSE is disabled by default, except when it's required to maintain compatibility with your output device … verify bit-perfect playback using Roon's Signal Path" (DSP engine article). DeaDBeeF skips ReplayGain on DoP streams (`replaygain.c:44-46`).
- **Why it matters:** The founder's daily driver is Pure on headphones; leveling is the first feature the founder will expect to "just work" there. If Leveling is implemented only in the kernel, Pure silently has none; if it is implemented on the device loan without telling the loan, the loan's "listener change stands" rule will adopt the leveling cut as the new anchor and the next track's cut compounds.
- **Severity:** must resolve before R1.1-B.
- **Recommended resolution:** Decide it in the story: on Pure, Leveling = a **cut-only offset on the existing device-volume loan** (MPD's `mixer` handler pattern; JRiver's and Roon's "almost all material gets quieter" makes cut-only viable), with the loan taught that its own leveling moves are not the listener's, and the Signal Path readout saying "Leveled on the device, −4.2 dB". Alternatives: (a) Leveling is Enhanced-only and the Pure badge says "Leveling off (bit-perfect)"; (b) a quantised cut (device steps are coarse — the loan already tolerates `sameLevel = 0.05 dB`, `MasterGainOnPure.swift:179`).

### F2 — The BS.775 fold lands *after* the limiter, so R1.1-B plans a second ceiling instead of one
- **Our items:** R1.1-B #1 / US-R1F-08 (BS.775 fold, "a safety ceiling after the spatial stage (C-43)"), the limiter, leveling of multichannel content (C-45), S18 (replaces the fold in the same slot).
- **Type:** complication.
- **Evidence — ours:** graph order `effectsAU → spatialAU → mainMixer` (`AudioEngineBridge+Graph.swift:64-73`); the limiter lives in the effects AU (`DSPKernel.cpp:325-331`); the spatial kernel only copies (`SpatialRenderKernel.cpp`, `routeBinauralStub`, no gain, no ceiling). The plan's second ceiling: `docs/product/backlog.md:1732-1737` (docs only — not in code).
- **Evidence — theirs:** BS.775-4 Table 2: L′ = L + 0.7071 C + 0.7071 LS (centred content sums to +3 dB per side). mpv: "`--audio-normalize-downmix` … If this is disabled, downmix can cause clipping. If it's enabled, the output might be too quiet." CamillaDSP folds with explicit per-source gains in dB (its stereo→mono example uses −6 dB each). JRiver: "Output Format … must be processed first" (DSP Studio). Roon: Headroom Management fixed at the top, one place.
- **Why it matters:** Two limiters in series on surround files (and one on stereo) means surround material gets a different, more compressed treatment; the leveling gain and the EQ's −ΔL are computed on the N-channel program, then the fold adds up to +3 dB on centred vocals, which only a second limiter can catch — exactly the "transparent leveling that compresses" the council flagged (C-38).
- **Severity:** must resolve before R1.1-B (it is the next sprint).
- **Recommended resolution:** Fold **before** the limiter — run the BS.775 matrix at the processing width inside the kernel (a fixed first "Output Format" stage, JRiver-style) so one ceiling, one place, and the leveling / −ΔL gains see the signal that reaches the device; keep the BS.1770 channel weights on the pre-fold analysis (C-45). Alternatives: move the limiter into the spatial AU (one ceiling, but the EQ-only ceiling rule moves with it); or mpv's choice — normalise the fold (−3 dB on everything) and accept "too quiet".

### F3 — Loudness compensation (S14-lite) needs a calibrated level it can own; our volume sits *after* the kernel and Pure bypasses it
- **Our items:** S14-lite / US-TON-03 / US-ADAPT-03, Master Gain (both paths), the ±12 dB trust clamp.
- **Type:** contradiction (between the story's inputs and where our gain lives) + complication.
- **Evidence — ours:** US-TON-03 "Compensation updates on every volume change event"; US-ADAPT-03 "Volume is monitored via system volume API … and the in-app volume control" (`backlog.md:552-560, 655-663`); the roadmap defers exactly that: "S14's adaptive half (the system volume observed, engine events) waits for W2" (`docs/product/roadmap.md`, R2 table); architecture §9: "requires a per-device SPL calibration" (all docs only). In code the kernel never sees Master Gain: it is applied at the mixer input downstream (`AudioEngineBridge+MasterGain.swift:45` + Apple `AVAudioMixing`), and the device volume is read only by the Pure loan (`DeviceVolumeControl`, `MasterGainOnPure.swift:59-73`).
- **Evidence — theirs:** JRiver couples Loudness to **Internal Volume** and a user **reference-level calibration** ("Enter the volume level that delivers the reference level … This reference level will also be used if you enable 'Loudness'"). CamillaDSP's Loudness "reacts to the configured fader"; it has a `reference_level`, scales the boost linearly over the 20 dB below it, and — the decisive sentence — "If the external volume control is placed after CamillaDSP in the audio chain, then the boost … may cause clipping. To avoid this, set `attenuate_mid` to true. That makes the loudness filter attenuate the midband instead of boosting the extremes." EasyEffects' Bass Loudness has a "Link" that adjusts output to keep the balance. Roon ships **no** loudness compensation at all.
- **Why it matters:** Without a level input the compensation is a static bass/treble tilt — the "Loudness" preset the team already renamed to avoid this confusion (decision 31). With a boost form inside the ±12 dB clamp it also eats the EQ's and the correction's boost budget and drives the limiter.
- **Severity:** must resolve before S14-lite.
- **Recommended resolution:** S14-lite's level input = **Master Gain (dB) + the device's own volume (dB)** read through the HAL seam the Pure loan already has, relative to a one-time **user reference** ("this is my normal loud setting", JRiver's calibration — no SPL model); and because our volume is downstream of the kernel, use CamillaDSP's **attenuate-mid** form (cut the mids as the level drops, never boost the extremes), which needs no headroom, cannot clip, and stays out of the ±12 dB boost clamp. State plainly that on Pure there is no compensation. Alternatives: boost form with its own pre-gain (then F4's ledger must own it); or wait for W2 and ship S14-lite as a manual "Loudness amount" slider.

### F4 — Gain staging: five gain stages today, three more planned, and no single owner of headroom
- **Our items:** EQ −ΔL (shipped), the AGC makeup (shipped), R1.1-B leveling gain, S12 AutoEq preamp, S13 correction layer, S14 compensation ("its own headroom or a cap"), the limiter's EQ-state-dependent ceiling, Master Gain.
- **Type:** overlap (several stages answer "how much pre-gain?") + complication.
- **Evidence — ours:** −ΔL is *loudness*-based (`TrackLoudnessGain.h:6-7`), computed from the graphic design only (`:81`); the AGC makeup is −20…+12 dB (`LoudnessModule.h:55-56`); the limiter ceiling changes with the path (−0.1 vs −1 dBTP, `OutputCeiling.h`, `DSPKernel.cpp:257-259`); EQ points clamp at ±12 (`EQBands.swift:26`, `EQCurve.swift:43-52`). Planned stages: `roadmap.md` R2 table (S14 "with its own headroom or a cap"), `sprint-plan.md` S12/S13 rows (docs only).
- **Evidence — theirs:** AutoEq's preset *starts* with `Preamp: -6.1 dB` and the code writes `f'Preamp: {-compound.max_gain:.1f} dB'` — a **peak-based** preamp (`frequency_response.py:211`; HD 650 file); its filters go to ±20 dB (shelf/peaking) and the README example runs `--max-gain=24` (`constants.py:49-57`). Equalizer APO: preamps "sum in dB", for "filters with positive gain, to make sure that no clipping occurs". Roon: a fixed-position Headroom stage, "Start by setting the Headroom adjustment to −3dB", a clipping light, and three named causes (louder filters, inter-sample overs, minimum-phase processing). JRiver: volume reduction *is* the headroom. Strawberry has a dedicated `equalizer_preamp` volume element before its EQ. FabFilter Pro-Q's Auto Gain "is an educated guess based on the current EQ settings, and is not a dynamic process based on actually measured levels".
- **Why it matters:** An imported HD 650 correction asks for a +6.4 dB low shelf and a −6.1 dB preamp. If our chain treats it as EQ points, two things go wrong at once: gains beyond ±12 are **silently clamped** (the "picture lies" anti-pattern the team's own research flagged), and the *loudness*-neutral −ΔL will typically be smaller than the *peak*-based preamp, so bass-heavy tracks reach the limiter — which on the EQ-only wired path sits at −0.1 dBTP and then acts as a program compressor (the very thing LD-17 forbids).
- **Severity:** should resolve before S12 (the design decides S13 and S14 too).
- **Recommended resolution:** One off-RT **headroom ledger** in the Realizer: pre-gain = the most negative of {−ΔL, −(max boost of the correction/import), leveling gain}, applied **once, before the EQ** (Roon's fixed first stage; EAPO's summed preamp), with the limiter kept as a safety whose gain reduction is **metered and shown** (Roon's light; architecture §9 already promises "metered limiter gain-reduction"); correction gains are exempt from the ±12 *point* clamp but counted by the ±12 *total-boost* trust clamp as a preamp — never clipped silently. Alternatives: Pro-Q-style static estimate per curve (cheaper, no track analysis); or keep separate stages but display the sum.

### F5 — Intensity is a macro over a *utility* stage (the normaliser) — nobody else does that, and the S17 text is already stale
- **Our items:** S17 / US-RMG-02 ("Map intensity 0→1 across loudness-comp + clarity (+ crossfeed)"), C-40 (+2–3 dB blend bump), S14 loudness compensation, R1.1-B leveling, crossfeed.
- **Type:** contradiction (docs vs code) + complication.
- **Evidence — ours:** the normaliser has no on/off of its own — it runs whenever Intensity selects P2 or the blend (`TargetState.h:64`, `DSPKernel.cpp:263-270, 316-318`), and its contribution is faded by Intensity (`DSPKernel.cpp:37-43, 294-299`); the blend "adds up to +3 dB at r = 0.5 … which the normaliser downstream absorbs" (`DSPKernel.cpp:285-288`) — but with leveling Off by default (FD-2) nothing absorbs it. The sprint plan's S17 row still maps crossfeed into Intensity (`docs/sprints/sprint-plan.md:112`), while the code moved crossfeed *out* ("at its preset's full strength whatever Intensity is", `DSPKernel.cpp:207-209, 321-324`).
- **Evidence — theirs:** Roon: no macro; per-filter switches ("Toggling filters on and off is great for A-B testing"); Volume Leveling lives in Zone settings *outside* MUSE. JRiver: per-block checkbox; Volume Leveling fixed first. EasyEffects: global + per-effect bypass. Pro-Q's one macro, Gain Scale, "only affects the EQ shapes that actually offer a gain setting … It will not affect the other filter types" — a macro over *shape*, never over level. CamillaDSP scales loudness compensation by **level** (reference − 20 dB), not by a taste knob.
- **Why it matters:** If S14's compensation is inside the Intensity map, two controls change timbre (Master Gain via the level, Intensity via the fraction) and the user cannot tell which one "won". A level stage inside an equal-power blend also makes "transparent" leveling depend on the knob position.
- **Severity:** should resolve before S17 (and the S17 row should be corrected now).
- **Recommended resolution:** Intensity scales only the **perceptual** stages (Clarity depth, BRIR room amount, width); leveling and loudness compensation are level/utility stages with their own switches outside Intensity (Roon's Zone-level leveling), so the blend has no level stage to "absorb" and C-40's bump is solved by the correlation-compensated law alone. Correct the S17 text ("+ crossfeed" is gone). Alternatives: keep compensation in the map as the architecture's "fraction of the contour difference", but then document that Intensity 0 = no compensation and show both numbers in the signal path.

### F6 — Graphic + parametric "alongside" + a correction layer = three filter sets with one loudness-neutral gain that only knows the graphic
- **Our items:** S12 (parametric bands alongside the 31-band, AutoEq import, `EQProgram`/`FilterSpec`), S13 ("a correction layer and the user's taste on one graph"), US-PROF-02 (whole-chain A/B), the per-output pin.
- **Type:** complication.
- **Evidence — ours:** `TrackLoudnessGain::onDesign(const GraphicEQDesign&, bool)` (`TrackLoudnessGain.h:81`); the drawn/sent curve is base + Tone clamped (`EQCurve.swift:43-52`); hold-to-Compare is EQ-only (`backlog.md` US-PROF-02 — docs only); S12/S13 rows (`sprint-plan.md:82-83`, docs only).
- **Evidence — theirs:** Equalizer APO: `Filter`, `GraphicEQ`, `Convolution` and `Preamp` are commands in **one ordered list**, `Include` "so that you can e.g. set a preamp before". Roon: PEQ, Procedural EQ, Convolution and Audeze presets are **separate, re-orderable filters each with its own switch**. EasyEffects: one parametric (1–32 bands, IIR/FIR/FFT) and the user orders effects. AutoEq exports graphic *and* parametric forms of the same correction. (The team's own survey adds Poweramp's "parametric presets can't load into graphic mode" and Wavelet's "correction first, taste second" — not opened this session, unverified.)
- **Why it matters:** A correction curve neutralised for loudness by a gain that was fitted to a different filter set will drift; a user who edits the graphic on top of a correction has no per-layer bypass to hear what each did; the per-output pin currently remembers one curve, not "correction + taste".
- **Severity:** should resolve before S12.
- **Recommended resolution:** Make `EQProgram` an **ordered list of sections** — [correction (S13, device-keyed), taste-graphic, taste-parametric] — each with its own bypass and colour on the one graph, one preamp/−ΔL computed over the *composite* response, and the per-output pin storing the whole program; hold-to-Compare becomes "bypass this section" (Roon's switches), which also delivers US-PROF-02 cheaply. Alternative: AutoEq imports land as a *preset* in the taste layer (simplest, but then taste edits and correction are entangled, and the preamp story of F4 is lost).

### F7 — Crossfeed and BRIR (S18): declared mutually exclusive, no owner; crossfeed placement is right
- **Our items:** S18 (BRIR), US-SPAT-01 ("HRTF is default-on for any device classified as headphones"), crossfeed (shipped), the per-output memory.
- **Type:** complication.
- **Evidence — ours:** "crossfeed and a future binaural BRIR are MUTUALLY EXCLUSIVE … No arbitration code yet … When S18 BRIR ships, treat `crossfeed.enabled && brir.active` as a control-layer bug" (`TargetState.h:100-105`); crossfeed off by default, BRIR planned default-on for headphones (`backlog.md` US-SPAT-01 AC, docs only).
- **Evidence — theirs:** Roon's crossfeed "simulates the experience of listening to stereo speakers" — the same job as a BRIR, and it is one re-orderable filter the user switches. Strawberry puts bs2b **last**, after the software volume; EasyEffects lets the user order it. bs2b's own output gain (`gain = 1/(1 − G_hi + G_lo)`, `bs2b.c:179, 213-214`) keeps centred bass at unity and never boosts — our module folds the same gain (`CrossfeedModule.h:30-32`), so placing it before the limiter costs nothing.
- **Why it matters:** Two head-related cross paths stacked is a smeared centre and a dull top; a default-on BRIR that silently overrides a chosen crossfeed is the kind of "it changed my sound" surprise the faithful-by-default rule exists to prevent.
- **Severity:** should resolve before S18.
- **Recommended resolution:** S18 adds the arbitration in the Realizer: BRIR on ⇒ crossfeed forced off, both shown in the signal path, the choice remembered per output like the EQ pin; keep crossfeed as the last stage before the limiter. Alternative: make them one "Headphone rendering: Off / Crossfeed / Room" control (one owner, no conflict possible).

### F8 — Leveling semantics (R1.1-B): no Auto mode, no declared target, no unknown-loudness fallback, tags undecided — every mature player has all four
- **Our items:** US-R1F-10, `kDefaultLufsTarget`, TrackLoudnessKit, the causal estimate.
- **Type:** overlap / gap.
- **Evidence — ours:** target −16 LUFS (`AudioConstants.h:34`); Off / Album / Track only, "Open: whether ReplayGain / R128 tags, when present, take precedence" (`backlog.md:1752-1763`, docs only); a failed analysis falls back to a live causal estimate slewing ≤ 1 dB/s (`TrackLoudnessGain.h:14-15, 24`).
- **Evidence — theirs:** Roon: Off / **Auto** ("track adjustments when playing adjacent tracks from different albums, and album level adjustments when playing adjacent tracks from the same album") / Track / Album; "Volume adjustment when loudness is unknown" default **−5 dB** "prevents large changes in volume when transitioning from content of known loudness to content of unknown loudness"; target −14 LUFS; ReplayGain tags read (relative to −18 dBFS). JRiver: album gain when playing an album, per-track in mixed playlists; −23 LUFS. Spotify: −14; album as a whole, track when shuffling. foobar2000: "by playback order" source mode; −18 LUFS scanner "to retain compatibility with the ReplayGain standard". Audacious `Automatic` (track when shuffling); DeaDBeeF "by playback order"; MPD `auto` (track when random) plus `replay_gain_missing_preamp`; mpv `--replaygain-fallback`.
- **Why it matters:** Album vs Track is the wrong question to ask a listener; the answer depends on what is playing next (shuffle vs album), which is why every player derives it. A live estimate for an unanalysed track moves the level *during* the song — Roon's fixed fallback does not.
- **Severity:** should resolve before R1.1-B.
- **Recommended resolution:** Ship **Off / Auto / Album / Track** with Auto = Roon's rule (album when the adjacent tracks share an album, else track); a fixed "unknown loudness" fallback (−5 dB) instead of the live estimate when leveling is on; pick and *display* the target (−14 LUFS matches Roon/Spotify; −18 matches ReplayGain files); read R128/ReplayGain tags when present (every open-source player does; Roon opt-in). Alternative: keep Album/Track but make the default follow shuffle (DeaDBeeF's rule) without a visible Auto.

### F9 — The limiter ceiling moves with the EQ state, and an unmeasured sample-rate conversion runs after it
- **Our items:** the EQ-only ceiling (decision 29), Intensity (S17), the Engine sprint.
- **Type:** complication (note).
- **Evidence — ours:** −0.1 dBTP on a wired/built-in output at P1, −1 dBTP elsewhere and on every other path (`OutputCeiling.h:19-40`, `DSPKernel.cpp:251-262`); "a device not at 48 kHz still gets AUHAL's own output-side conversion (unmeasured; the Engine sprint runs the graph at the device rate)" (`architecture.md` §2.5, docs only).
- **Evidence — theirs:** Roon names "inter-sample overs … after upsampling" as a clipping cause and starts headroom at −3 dB; HQPlayer's developer: never above −3 dBFS (secondary source); EBU R128: −1 dBTP, and "Permitted Maximum True Peak Levels may be lower for different distribution systems"; Spotify's limiter engages at −1 dB (sample values).
- **Why it matters:** Moving Intensity from 0 to just above 0 changes the ceiling by 0.9 dB on a loud master — a level step hidden inside the knob; and a −0.1 dBTP signal leaves ~0.3 dB of real margin before a conversion nobody has measured. Nobody else runs a ceiling above −1 dBTP.
- **Severity:** note (re-check in the Engine sprint, when the graph runs at the device rate).
- **Recommended resolution:** Keep −1 dBTP everywhere until the Engine sprint removes the hidden conversion and measures it; if the "EQ On sounds quieter than Off" problem (decision 29's reason) remains, solve it with the ledger's pre-gain and a displayed GR meter rather than a moving ceiling.

### F10 — Device-class gating (crossfeed now, correction and BRIR next) where others use per-device *memory* plus a manual override
- **Our items:** crossfeed gating (shipped), US-R1F-12, S13 auto-load by identified device, US-SPAT-01 default-on by class.
- **Type:** contradiction (docs vs code) + note.
- **Evidence — ours:** `crossfeedPlays = crossfeedEnabled && deviceIsHeadphones` (`AudioViewModel.swift:233-235`; `AudioViewModel+Devices.swift:24-32`), whereas US-R1F-12's acceptance says "It can be enabled on any output" (`backlog.md:1776-1786` — docs only, not what the code does). The EQ already has the right pattern: a per-output pin with a model-UID fallback (`EQOutputPin.swift:4-29`).
- **Evidence — theirs:** Roon, Strawberry, EasyEffects and CamillaDSP never gate crossfeed by device class — it is a filter you switch. Equalizer APO's `Device:` command selects a configuration per output device, with the pattern "all" always matching — per-device memory with an explicit catch-all.
- **Why it matters:** A DAC feeding headphones is "USB", a wired pair in the jack was "built-in" (KI-DEV-01): classification is a heuristic, and a heuristic that *forbids* a choice is worse than one that *suggests* it.
- **Severity:** note (should be settled when S13 designs the correction auto-load).
- **Recommended resolution:** Per-output memory (the EQ pin) for crossfeed, correction and BRIR alike, with the device class only choosing the *default* for a never-seen output and a manual override that always wins; align the US-R1F-12 text with the code or the code with the text.

### F11 — Something nobody ships: a loudness-neutral EQ gain measured from the track itself
- **Our items:** EQ −ΔL (decision 26), the hold-to-Compare, R1.1-B leveling, F4's ledger.
- **Type:** note (a differentiator with a cost).
- **Evidence — ours:** `TrackLoudnessGain.h:3-33` (per-track gain from the analyzer's prefix then the whole track, 10 ms / 500 ms / 2 s glides, gapless groups share one gain if the seam step would exceed 0.2 dB).
- **Evidence — theirs:** Pro-Q's Auto Gain is "an educated guess based on the current EQ settings, and is not a dynamic process based on actually measured levels"; AutoEq / Equalizer APO use a static peak preamp; Roon's and Spotify's leveling gains are one constant per track/album; Strawberry's EQ preamp is a fixed `volume` element.
- **Why it matters:** The gain is correct and the A/B is fairer for it — but it is a *second* per-track level stage next to leveling, with its own glide rules and seam-sharing logic; two owners of level is what the council's C-38 was about.
- **Severity:** note.
- **Recommended resolution:** Keep it, but as a **leveling-class entry in the ledger** (F4) so leveling and −ΔL are one published gain with one glide law; alternatively replace it with a Pro-Q-style static estimate per curve when leveling is on (leveling then owns level, the EQ owns shape).

## 3. Where others agree with the plan (coverage, so these need no further debate)

- **Leveling as a static per-track/album gain from analysis, true-peak-capped, off by default** (R1.1-B): Roon ("simple gain adjustments … modified to avoid clipping … 'true peak'"; "not enabled by default"), JRiver ("does not compress … just changes playback volume"), foobar2000 / MPD / Audacious / DeaDBeeF / mpv (peak-based clipping prevention), Spotify (TP-limited positive gain). FD-2's replacement of the session AGC is the industry shape.
- **A true-peak safety limiter at −1 dBTP, no program DRC by default** (LD-17): EBU R128 (−1 dBTP), Spotify (limiter only in its Loud mode), EasyEffects (limiter is an optional effect).
- **Master Gain turn-down only, dB-linear, applied after the DSP**: Strawberry's software volume after its EQ; JRiver's internal volume giving headroom; Audirvana's 64-bit internal volume; mpv's software mixer. Applying it at the mixer input (after the limiter and the fold) is the safe place.
- **Pure = no DSP; volume on the device, not the stream**: MPD's `replay_gain_handler=mixer`, Audirvana's device volume, JRiver's "does not work when bitstreaming", Roon's signal-path honesty. Our loan with a never-exceeded ceiling is stricter than any of them.
- **bs2b crossfeed with bs2b's own gain law and presets**: Strawberry and EasyEffects ship the same library and presets; the folded gain in our module matches `bs2b.c:179`.
- **Faithful by default** (FD-2): Roon "MUSE is disabled by default", Roon leveling off by default, Audirvana software volume off by default.
- **AutoEq import in `ParametricEQ.txt` form, with the Preamp line** (S12): the file format is exactly `Preamp:` + `Filter n: ON PK/LSC/HSC Fc … Gain … Q …`; Equalizer APO reads it directly.
- **Loudness compensation as level-keyed shelving with a reference level and a cap** (S14): CamillaDSP/RME (shelves at 70 Hz / 3.5 kHz, 10 dB default, reference − 20 dB window), JRiver (reference-level calibration), EasyEffects (ISO 226 contours by output volume). The architecture's "fraction of the ISO 226 contour difference" is the more principled version of the same thing.
- **Headroom as an explicit, visible stage** (planned in S14 "its own headroom or a cap"; the review asks it to be one stage for everything — F4): Roon, JRiver, Equalizer APO, AutoEq, Strawberry all have one.
- **Analysis at import/load, cached**: JRiver auto-analyses on import; Roon's Audio Analysis; our `TrackLoudnessAnalyzer` prefix-then-whole is finer-grained than either.
- **The −14 LUFS neighbourhood for a music target**: Roon (−14), Spotify Normal (−14); our −16 sits between them and foobar2000's −18 — not wrong, just undeclared (F8).
