## Findings

### LIB-01 No reactive read layer: `libraryRevision` + 8 hand-copied epoch loaders + views deciding when to reload, STRUCTURAL. Criteria: 1, 2, 3, 5
- **Evidence:**
  - Invalidation signal: `LibraryModel.swift:69` `var libraryRevision = 0`, bumped by hand at `LibraryModel+Metadata.swift:37` and `LibraryModel+Scan.swift:173` (24 references app-wide). It is a second hand-made signal next to `AudioViewModel.playCountRevision` (`+PlayTracking.swift:74`, consumed by `QueueHistoryList.swift:57`) and the explicit `await loadTree()/loadDetail()` calls after every playlist mutation (`PlaylistsModel.swift` at 6 sites).
  - Consumers re-implement "reload once per revision" separately: `LibraryBrowseModel.swift:161,376` (`lastLoadedRevision`), `PlaylistsModel.swift:79,134`, `MusicFoldersSection.swift:48`, `LibraryDetailPage.swift:60` (`.task(id: libraryRevision)`), `LibraryTabView.swift:52`.
  - The newest-wins loader is copied 8 times: `loadRoots:233`, `loadAlbums:260`, `loadSongs:294`, `runFilter:360`, `LibraryBrowseModel+Facets.swift loadFlatFacet` (artists, genres), `+History.swift loadHistory`, `PlaylistsModel.loadTree:108`, `loadDetail:245`. Each is: bump epoch, capture, await, guard, publish, set a `LoadState`. There are 7 epoch ints in `LibraryBrowseModel` plus 2 in `PlaylistsModel`, and two different `LoadState` enums (`LibraryBrowseModel.LoadState` with `firstRun`, `PlaylistsModel.LoadState` without).
  - Who reloads is split: `reloadIfScanChanged()` lives in a model but is triggered by `LibraryTabView`'s `.onChange` (so only while that view is mounted); per-list `.task`/`load:` closures reload on appear. Freshness is a protocol between view lifecycle and model, enforced nowhere.
- **Root cause:** The store is a request/response repository. Nothing says "this data is derived from these tables, tell me when it changes", so each model re-derives an invalidation signal by hand and guards races with counters. The `searchEpoch` doc (`LibraryBrowseModel.swift:~130`) says "`.task(id:)` cancellation alone can't interrupt an in-flight actor call, hence the epoch". That was true of the retired actor-based SQLite wrapper. It is false now: GRDB's async `read` is cancellable (`GRDB/Core/DatabaseReader.swift:216`, "`CancellationError` if the task is cancelled"; `SerializedDatabase.swift:256` uses `withTaskCancellationHandler`). The epochs are a fossil of the pre-GRDB design.
- **Why it matters:**
  - Every new list (R2 will add several) copies the pattern and its subtle two-suspension-point re-guard (`loadFlatFacet` exists solely to keep that correct).
  - Coarse invalidation: any pass end reloads all four full lists (`reloadIfScanChanged`: albums, songs 20k rows, artists, genres) plus playlists, even when one file changed (see LIB-08).
  - During a first scan the browse stays empty until the whole metadata pass ends, because the only bump is at pass end. A fine-grained observation would fill live.
  - Inconsistent snapshots: the models issue several separate reads (see LIB-09).
- **Structural remedy:**
  1. Use GRDB's own mechanism: `ValueObservation.tracking { db in ... }` per list, consumed with `for try await value in observation.values(in: store.dbWriter)` inside one model-owned `Task` per slot. GRDB handles region tracking, coalescing, and ordering; newest-wins is intrinsic (it re-reads on change and delivers in order); cancellation is the Task. `libraryRevision`, `playCountRevision`, all epochs and `lastLoadedRevision` disappear. GRDB docs: `ValueObservation` DocC, `Documentation/Concurrency.md`; GRDB's own demo app (`Documentation/DemoApps/GRDBDemo`) uses exactly this for a list model.
  2. Keep the store's `Database` private by exposing named observation factories (`func observeAlbums(sort:) -> ValueObservation<...>`), or `AsyncStream`s, from `LibraryStore`.
  3. Even without ValueObservation, collapse the 8 loaders into one `LoadSlot<Value>` (struct with state + a `Task` handle; `load { try await ... }` cancels the previous task). That is ~40 lines, and removes the epoch ints.
  4. Move the "when to reload" decision out of the views into the model.
- **Effort:** L (ValueObservation migration, one list at a time is fine), M for the LoadSlot-only variant. **Risk:** med (ordering/flash behaviour is heavily hand-tuned and described in comments; the break-it suite would need re-running). **Depends on:** LIB-09 (compose reads in one snapshot).

### LIB-02 Sweep deletes on "absence from a walk" with no evidence the walk was complete, STRUCTURAL. Criteria: 1, 4, 6
- **Evidence:**
  - `LibraryScanner.swift:131-135` `FileManager.default.enumerator(at:..., options:)` is created with no `errorHandler`; the enumerator silently skips unreadable subtrees and ends early if the volume goes away mid-walk.
  - The only completeness check is `walked.filesSeen == 0, preCount > 0` (`LibraryScanner.swift:~90`), which catches ONLY a total failure.
  - `store.sweepOrphans` (`LibraryStore+DAO.swift:267`) then `DELETE`s every row of the folder with an older stamp. `tracks` rows cascade-delete `playlist_entries` (`ON DELETE CASCADE`, schema v3), and the row carries play_count / loved / rating / frecency.
  - A partial walk is easy to produce: an unreadable or permission-changed subfolder, a NAS share dropping halfway, an iCloud-evicted directory, a sub-volume mounted under the root that goes away.
- **Root cause:** Deletion is inferred from absence and applied immediately and irreversibly. The G-LIB-01 fix (never lower a stamp) and the empty-walk guard patch the two cases found; the design still has no notion of "this walk is trustworthy" or "this row is missing, not gone".
- **Why it matters:** User data (playlists, play history) is the ONLY non-rebuildable thing in the store, and it hangs on the least reliable signal. The same design also loses ids on a cross-root move whose old root is swept first (see LIB-03).
- **Structural remedy:** Two layers, in order of cost:
  1. Make the walk report completeness: pass an `errorHandler` to the enumerator that records and then fails the walk (or marks it "incomplete") so the sweep is refused on ANY enumeration error; add a proportional guard (refuse a sweep that would delete > N% of a folder's rows unless the walk was explicitly confirmed).
  2. Replace delete-on-absence with a `missing_since` tombstone (nullable column, additive migration v8): a sweep marks, browse queries filter `missing_since IS NULL`, a GC job deletes rows missing for more than X days or after the folder has been walked clean twice. This gives partial walks, unmounted volumes, and cross-root moves a recovery window and lets playlists show "missing" via the existing Locate flow instead of silently dropping the entry. Mature reference: Navidrome's scanner marks absent files `missing` and keeps annotations and playlists (github.com/navidrome/navidrome, scanner rewrite in 0.55; verify details). Music.app likewise keeps the track and shows "!".
- **Effort:** S for 1, L for 2. **Risk:** low for 1, med for 2 (touches every read's WHERE and counts). **Depends on:** none. Hand the sweep/generation/move-match semantics to the algorithm panel (N30, N36-N40, N44).

### LIB-03 Move-match is walk-order dependent and global-scoped but sweep is folder-scoped, SIGNIFICANT. Criteria: 4, 1
- **Evidence:** `LibraryStore+MoveMatch.swift:~28` `moveCandidateSQL ... AND last_seen_scan < ? ...` matches across ALL folders (not scoped to the walking folder); `beginScanGeneration` (`DAO:167`) is `max(last_seen_scan)+1` over the whole table, read in a separate transaction from the stamps (two concurrent walks of different folders, which `FolderWalkSchedule` allows, get the SAME generation). Sweep is `folder_id IN (?) AND last_seen_scan < ?`.
- **Why it matters:** A file moved from root A to root B keeps its id only if B's walk runs before A's sweep. If A reconciles first, A's sweep deletes the row (with user data) and B inserts a new id. Same-folder moves are fine. The generation is neither unique nor reserved, so "older than generation" has different meaning per folder. The existing tests (VLS `ChecksMoveMatch`) cover single-root cases; the cross-root ordering is an unproved property.
- **Structural remedy:** Per-walk token: allocate the generation inside the same write that begins the walk and make it unique (a `scans` table or an in-store counter row), and defer deletion (LIB-02 tombstone) so a later move-match can resurrect a `missing` row regardless of order. Flag for the correctness panel (N36-N40).
- **Effort:** M. **Risk:** med. **Depends on:** LIB-02.

### LIB-04 Production `LibraryStore` carries ~25 test-only "verification hooks" and ~20 app-dead public operations, SIGNIFICANT. Criteria: 3, 6, 1
- **Evidence:** Mechanical check of every public/internal store method against app + LibraryScan + LibraryBrowseKit call sites (non-comment). Zero production callers:
  - Test hooks: `countRows`, `seedFolderRow`, `setUserState`, `userState`, `frecencyState`, `journalMode`, `foreignKeysEnabled`, `busyTimeout`, `integrityCheck`, `schemaVersion`, `searchIndexWriteCount`, and 7 `explain*Plan` (`LibraryStore.swift:62-175`, `BrowseReads:~340-400`). They are public API on the production class, in the same file as the facade, with a `Mutex` counter (`searchIndexWrites`) incremented on every FTS write in release builds.
  - App-dead operations: `addLooseFile`, `allTracks`, `tracks(inFolder:)`, `track(url:)`, `upsert`, `classify` (only used inside `upsertReconciling`), `delete(id:)`, `moveCandidate`, `moveMatched`, `appendEntry`, `insertEntry`, `clearEntries`, `playlistCount`, `bootstrapBuiltinCurrentPlaylist`, `albums(byArtist:)`, `albums(inGenre:)`, `applyMetadata` (non-pass path, plus its `.sameTitles` regroup branch), and the whole playlist-folder DAO (`createFolder`, `renameFolder`, `reparentFolder`, `deleteFolder`, `restoreFolderSubtree`, `setPlaylistFolder`, `folders`: `LibraryStore+PlaylistFolders.swift`, 266 lines, plus schema v5 and 238 lines of harness checks). The app target has no reference to playlist folders at all.
  - Periphery cannot flag any of this because `VerifyLibraryStore` (an executable target) uses them.
- **Root cause:** The harness is the second client of the store and drove the API; nothing distinguishes "public API of the module" from "what the harness needs". Dead-feature DAO code stayed after the UI for it was dropped (the glass sweep).
- **Why it matters:** Every dead method is code that has to be kept correct (e.g. playlist-folder CASCADE semantics, the `.sameTitles` path that production never takes yet shapes `AlbumUpkeep`), and the public surface hides what the app depends on. It also hides real gaps: the app calls `moveTrack` once and `incrementPlayCount(url:)` once.
- **Structural remedy:** (a) Put hooks behind `package` access (Swift 5.9, same package), or a `LibraryStore.Diagnostics` view obtained from an `internal`/`package` accessor, so the public module API is exactly the app's use. (b) Decide the playlist-folder feature: remove the DAO and harness checks (the v5 tables must stay: frozen migrations), or schedule the UI. (c) Delete dead single-track variants where the harness can use the batch form.
- **Effort:** M. **Risk:** low. **Depends on:** none.

### LIB-05 Cross-library search is dead; three different filter semantics are live, SIGNIFICANT. Criteria: 3, 1
- **Evidence:** `LibraryStore+Search.swift:search(_:)` (the sectioned tracks/albums/artists bm25 read) has 0 app callers (34 harness). Live: Songs filter = FTS5 prefix-AND tokens (`searchMatchingIDs`, `ftsMatchQuery`); Albums/Artists/Genres/queue filter = `FacetTextFilter` (`localizedStandardContains`, substring, in memory, `LibraryBrowseKit/FacetTextFilter.swift`).
- **Why it matters:** The same typed text behaves differently by tab: "ear" matches "Pearl Jam" in Artists (substring) and not in Songs (prefix of a token). Founder decision (see Open questions).
- **Effort:** S (delete) or M (unify). **Risk:** low. **Depends on:** a product decision.

### LIB-06 `FolderWalkSchedule` is the right abstraction, but the scan/reconcile pipeline around it is still a model-owned state machine of 8 mutable collections, SIGNIFICANT. Criteria: 1, 2, 6
- **Evidence:** `FolderWalkSchedule` (`LibraryScan/FolderWalkSchedule.swift`) is pure, value-typed, documented with its rules, and tested without the app: good. What surrounds it in `LibraryModel` is not: `scanTask`, `walkSchedule`, `walkTasks`, `folderAddTask`, `reconcileDebounce`, `watchedRoots`, `reconcileState`, `isReconciling`, `lastReconciledAt`, `lastReconcileError`, `volumeMonitorTokens`, spread over 6 files (`LibraryModel*.swift`). The legal transitions (add cancels? reconcile owed? remove vs running walk?) are split between the schedule (for walks) and ad-hoc `Task` handling in `removeLibraryFolder` (`beginRemoving`/`endRemoving` pairs, `LibraryModel+Scan.swift:~165-182`), `startFullMetadataPass` (cancel-and-await chain), `resumePendingMetadata` (`guard scanTask == nil`), `catchUpLibraryFolders` (awaits every `walkTasks` value). Three different "supersede" idioms.
  - `isReconciling` is a stored copy refreshed in `startWalks` only (`+Walks.swift:~45`); `walkEnded` calls `startWalks`, so it stays right, but it is a derived value stored by hand. `reconcileState` is written from 5 places and never read by any view (grep: the only reader of `reconcileState` outside LibraryModel is `LibraryModel+Scan.swift:168`, which clears it); `lastReconcileError` and `lastReconciledAt` have no reader either. The "paused root" state (the user-visible half of error recovery) is therefore invisible: a user whose NAS is unmounted sees nothing.
- **Root cause:** The schedule models only the "may a walk start" question. The metadata pass, the removal protocol, the debounce and the per-root status are not part of the state machine.
- **Why it matters:** Races between remove/add/re-add/metadata pass are exactly where G-LIB-01/05/06 came from; each new trigger adds a transition nobody can test (no test constructs a `LibraryModel`; the app target is not importable, see process.md).
- **Structural remedy:** Extend the pure schedule into the full "library activity" reducer: events (`requestWalk`, `walkEnded`, `metadataPassRequested/Ended`, `beginRemoving`, `volumeChanged`) → `[Command]` (start walk, cancel walk, start pass, cancel pass), with the per-root `ReconcileState` and `isReconciling` DERIVED from it. `LibraryModel` becomes a thin executor of commands (this is the Command/Elm-style pattern the charter names). Move it to `LibraryScan` next to the schedule so it is covered by `LibraryBrowseKitTests`. Surface `.paused` in the Music Folders row, or delete the dead state.
- **Effort:** M-L. **Risk:** med. **Depends on:** none.

### LIB-07 Persistence design: raw SQL + positional decoding where GRDB's record layer would carry the schema, SIGNIFICANT. Criteria: 1, 3, 5, 6
- **Evidence:**
  - 170 `sql:` call sites, 56 positional `row[N]` reads, and zero use of `Column`, `TableRecord`, `PersistableRecord`, associations or the query interface. `FetchableRecord` is used 9 times, each only as a positional `init(row:)`.
  - Positional contracts are held by comments: `BrowseReads.swift:~60` "Indices 0–16 MUST NOT shift; §12.1 APPENDS 17–21; S10.8 E appends 22"; `Reads.swift` "`duration_ms` is projected but unmapped (kept to preserve decode order)" (a column read that nothing uses); `selectGroupingRowsSQL` vs `GroupingRow.init`.
  - The title-fallback rule `COALESCE(NULLIF(title,''), name)` exists in four places: `LibraryTrackDisplay.init(row:)`, `Schema.backfillV2FtsStatement`, `searchRowSelect`, `singleKeyTrackOrder` (`BrowseReads.swift:304`). Same for the album "unknown" rules in SQL vs Swift.
  - Every SQL string is a `private static let` with its own doc line (a pattern, ~170), plus `selectTrackIDByURLSQL` defined twice (DAO and MoveMatch, with a comment excusing it).
- **Root cause:** The refactor from the hand-rolled SQLite wrapper kept the SQL and the positional decoding and replaced only the connection. GRDB is used as a better `sqlite3_exec`.
- **Why it matters:** Schema change risk (the v7 album change touched SQL in 6 files); drift that no compiler sees; no ValueObservation (needs a request or region, which raw SQL strings do supply via `SQLRequest`, but nothing does).
- **Structural remedy:** Not a rewrite. (1) Define the display-row projection ONCE as an enum of columns (`enum DisplayColumn: Int, CaseIterable`) and derive both the SELECT list and the decode from it. GRDB's docs rate positional access as the fastest path (`Row` doc, "Consume rows by index"), so keep it for the 20k-row hot read but generate it from one source. (2) Make `GroupingRow` / `AlbumFacet` etc. named-column records (`row["album_title"]`), which GRDB documents as the default; reserve positional for the one hot read. (3) Use `SQLRequest<LibraryTrackDisplay>` with `FetchableRecord` so the same request object feeds `fetchAll` and `ValueObservation` (LIB-01). (4) Pull the title-fallback into a SQL generated column or view (`v_track_display`) added by an appended migration; reading code and ORDER BYs then share it. GRDB docs: `Documentation/QueryInterfaceOrganization.md`, `GoodPracticesForDesigningRecordTypes` (DocC "RecordRecommendedPractices").
- **Effort:** M. **Risk:** low-med (the VLS gate has EXPLAIN checks and 80+ read checks). **Depends on:** none.

### LIB-08 Every FS change triggers a whole-root walk, a whole-library regroup and a full reload of four lists, SIGNIFICANT. Criteria: 1, 4, 5
- **Evidence:** `handleWatcherBatch` (`LibraryModel+Reconcile.swift:~85`) uses event paths only to pick the root; `performReconcile` then does `LibraryScanner().scan(root:)` (full enumeration + one `classify`/`upsertOne` round trip per file in 256-row transactions), then `runMetadataPass(inFolder:)` ends in `store.refreshDerivedFacets()`, which fetches EVERY track with an album title or album id (`selectGroupingRowsSQL(scope: wholeLibraryScope)`) and re-keys it in Swift (`AlbumGrouping.keys(for:)`), then `libraryRevision += 1`, then `reloadIfScanChanged` re-reads albums, songs (20k rows), artists, genres, plus `PlaylistsModel.reloadOnLibraryChange`.
- **Why it matters:** One new file (or a downloader rewriting a file and firing events for minutes, each followed by a 1 s debounce and a reconcile) costs O(library) at four layers: walk, regroup, 4 full reads, view diffs. At the 20k-song scale the brief benchmarks, each pass is likely 100s of ms of main-actor-visible churn plus lists re-publishing. Mature players use path-scoped incremental scans (the FSEvents batch already carries paths, `MustScanSubDirs` / dropped flags are decoded and unused: `WatcherEvent`). `FSEventStreamEventIdSinceNow` means launch catch-up also walks everything; the doc justifies this as a deliberate choice (`+Walks.swift:~30`), which is fair for correctness, not for per-edit cost.
- **Structural remedy:** Scope the reconcile to the changed subtree (walk `event.path` parents, sweep only that prefix; fall back to the full walk on `MustScanSubDirs`/dropped flags), incremental regroup keyed by the affected titles (the single-write path `regroupOwnAlbumLocked` already exists and is unused by production), and ValueObservation (LIB-01) so only affected lists re-read.
- **Effort:** L. **Risk:** med-high (the whole sweep/stamp model is path-scoped then; couples with LIB-02/03). **Depends on:** LIB-02, LIB-01.

### LIB-09 Store API granularity forces multi-read compositions that are not one snapshot, SIGNIFICANT. Criteria: 1, 4
- **Evidence:** Models compose several `await store.x()` calls, each its own transaction: `loadDetail` = `entries` then `tracksDisplay(ids:)` (`PlaylistsModel.swift:245-270`); `hydrateQueueOnLaunch` = `currentPlaylistID` then `entries` then `tracksDisplay` (`+QueueHydration.swift`); `loadAlbums/loadSongs/loadFlatFacet` = list read then `roots()` for firstRun-vs-empty (and re-guard after each suspension). `mirrorQueueNow` = `currentPlaylistID()` (a WRITE transaction, `builtinIDLocked` can seed) then `replaceEntries`.
- **Why it matters:** A sweep or removeRoot landing between the two reads yields an entry whose track is "unresolved" (shown as unavailable) or a firstRun/empty flash; the epoch machinery exists partly to hide this. GRDB's concurrency guide recommends one `read` closure for a consistent snapshot (`Documentation/Concurrency.md`, "Database Pool" / "Snapshots").
- **Structural remedy:** Repository methods shaped by use case, returning one value from one `read`: `playlistDetail(id:) -> (entries, displays)`, `queueSnapshot() -> [LibraryTrackDisplay]`, `browseList(kind:sort:) -> (items, hasRoots)`. Delete `currentPlaylistID()` as a public call (it writes); resolve it inside the DAO.
- **Effort:** S-M. **Risk:** low. **Depends on:** none (improves LIB-01).

### LIB-10 Migrations: strong guardrails, but two sources of version truth, hand-written provenance in each step, and an in-place amendment of a shipped-looking id, SIGNIFICANT. Criteria: 1, 6
- **Evidence:**
  - `currentSchemaVersion = 7` constant + `assert(steps.count == currentSchemaVersion)` + `schema_info.version` written by each of the 7 migration bodies (`writeSchemaInfo(db, version: N, ...)`) + GRDB's own `grdb_migrations` table (the real authority, used by `hasBeenSuperseded` etc.). Four representations of "which version".
  - v7 "was amended in place before any real library ran it" twice (`Schema+AlbumArtists.swift:1-5`), followed by `v7ShapeProblem` that REFUSES such a store forever at open (`StoreOpenRefusal.unfinishedTestVersion`). The write of the frozen-body rule ("NEVER edit a shipped migration body", `LibraryStore.swift:~245`) is correct, but v7 shows the guardrails (convergence fingerprint) don't stop an edit before release; the amendment cost permanent open-path code for a state that, post-R1, can never occur.
  - `Schema.swift` is the v1..v6 file at 492 lines mixing DDL constants, `MigrationID`, seed helpers, the FTS probe, and per-version functions in two idioms (static members in the type, then `public extension Schema`).
  - Header comment of `VerifyLibraryStore/main.swift` says "`swift test` is unusable here (swift-testing macro skew)": stale (memory: fixed 2026-07-02).
  - `derived_version` / `regroup_owed` are state flags in `schema_info` (the "provenance" table): `regroup_owed` is a work-queue marker, not provenance.
- **What is good here:** append-never-edit with an enforced fingerprint; the look-first read-only open with no checkpoint on close (`StoreSQLiteShim`) so a refused store is byte-identical; backup via `DatabaseReader.backup(to:)` with partial-file cleanup; typed `StoreOpenRefusal`; v7 rebuilt with FKs off and scoped `checkReferences`.
- **Structural remedy:** Treat GRDB's migrator as the single version authority (`migrator.appliedIdentifiers`); make `schema_info` carry only build/created_at; drop the per-step `writeSchemaInfo` (one post-migrate stamp in `openPool`). After R1 ships, delete `v7ShapeProblem` + `unfinishedTestVersion` (or keep one release then remove) and let `registerMigration(_:merging:)` squash if wanted (GRDB 7 API). Put `regroup_owed`/`derived_version` in a small `store_state` table on the next migration. Split `Schema.swift` per version (the v7 file already is).
- **Effort:** M. **Risk:** med (touches the migration list, which the gate fingerprints; must be done as an APPENDED migration plus code, never an edit). **Depends on:** R1 tag.

### LIB-11 FTS index is a hand-maintained denormalisation guarded by a comment, LOCAL. Criteria: 1, 6, 5
- **Evidence:** `LibraryStore+SearchIndex.swift` header: "HIDDEN PREMISE (guard at S10+): the artist/album/genre FTS columns are DENORMALIZED copies... correct only because those names are immutable natural keys". `syncSearchRow` is called at every write site by convention (upsertOne, moveMatchedLocked, applyMetadataLocked); the invariant is proved by an op counter (`searchIndexWrites`), not by a state check.
- **Why it matters:** R2 features that edit tags or merge artists (a likely roadmap item) silently desync search. GRDB documents the structural alternatives: external-content FTS5 with `synchronize(withTable:)` triggers (`Documentation/FullTextSearch.md`); they work for one source table, here the index spans four tables, so the explicit seam is defensible.
- **Structural remedy:** Keep the seam, but add an invariant check as a pure function plus a test: "FTS rows == projection of tracks" (`SELECT ... EXCEPT` both ways), run in the harness after every scenario and in a debug `-ASVerify` launch flag. Replace the production counter with that check.
- **Effort:** S. **Risk:** low.

### LIB-12 Queue mirror re-implements the coalescing writer that exists in the kit, SIGNIFICANT. Criteria: 3, 1, 6
- **Evidence:** `AudioViewModel+QueueMirror.swift:25-36` hand-rolls a debounce `Task` with `queueMirrorTask?.cancel()`; once the sleep has returned the task is not cancellable in effect (`mirrorQueueNow` never checks cancellation), so two snapshots can be in flight (debounce + quit-flush `+Lifecycle.swift:126`), and the older one can be enqueued after the newer. `LibraryBrowseKit/CoalescingWriter.swift` (162 lines of tests, "one write at a time, newest wins, flush") exists for exactly this and is used by `PlaylistsModel.orderWriter`.
- **Why it matters:** The queue is the app's most important persistent user state (restore-paused on launch). The failure window is small, but it is an unproven ordering, and the same job has two implementations with different guarantees.
- **Structural remedy:** Route the queue snapshot through `CoalescingWriter<Void, [Int64]>` (one writer, newest wins, awaited flush at quit). Also make `replaceEntries` take the built-in playlist implicitly (see LIB-09) and treat the built-in "current" playlist as what it is: a separate `queue_entries` concept. At present 34 `is_builtin` references (store + kit) exist so that the playlist tables can double as the queue: every playlist read, count, name rule, `unreferencedTrackIDs` and `removeRoot` has to remember the exemption (`PlaylistBrowseVisibility.userVisible` filters it at the app layer, `store.playlists()` returns it).
- **Effort:** S (coalescing), M (separate queue table; an appended migration + data copy). **Risk:** low / med. **Depends on:** none.

### LIB-13 Album-year and ordering rules live in two layers with opposite tie-breaks, SIGNIFICANT. Criteria: 3, 4
- **Evidence:** known from the map: `AlbumGrouping.dominantYear` (`LibraryStore/AlbumGrouping+Years.swift:25`, tie to the LATEST, the album's stored `albums.year`) vs `FacetAlbumGrouping.albumYear(of:)` (`LibraryBrowseKit/FacetAlbumGrouping.swift:~101`, tie to the EARLIEST) on artist/genre pages. New insight on the root cause: the kit version only runs when `albumYear == nil` on every row (`albumYear` is projected from `al.year` and is non-nil whenever the store derived one), so the two rules disagree only in the unlabelled corner (songs with no album-year); they are two implementations of one concept, tied together by nothing. In addition `AlbumTrackOrder`/`DiscFolder` (kit) re-derive "disc from folder name" that `AlbumGrouping+Names.albumFolder` (store) already folds, both pure string rules on the file path, tested separately.
- **Structural remedy:** One owner for album semantics: expose `AlbumGrouping` display/ordering helpers publicly from `LibraryStore` (or a tiny `AlbumKit` both import) and have the kit call them. One `dominantYear`, one disc-folder parser. Tests assert both layers via the one function.
- **Effort:** S-M. **Risk:** low. **Depends on:** none. Correctness panel: N49-N52, N56, N76.

### LIB-14 Error handling at the model boundary swallows store errors into "empty", LOCAL. Criteria: 6
- **Evidence:** `try?` on store reads that decide state: `loadRoots` (`LibraryBrowseModel.swift:236`, failure becomes `[]` i.e. "no folders"), `LibraryModel+Reconcile.swift:58` (`refreshWatchedRoots`: a read failure leaves `watchedRoots = []`, so the watcher stops watching everything and nothing says why), `LibraryModel+Walks.swift:59` (a failed `roots()` skips the walk), `runFilter` (silently keeps last-good), `facetRows` (a failed read returns `[]`, so Play of an album that failed to read is a silent no-op), `LibraryModel+VolumeMonitor.swift:51` (`try? restampRoot`).
- **Why it matters:** Failure collapses to a plausible empty state; the first-run CTA could appear over a real library after a transient busy error. The store itself is carefully typed (`StoreOpenRefusal`, `URLConflict`, `PlaylistMutationError`); the app boundary discards it.
- **Structural remedy:** One `LibraryModel.report(_ error:, context:)` used instead of `try?`; model reads return `Result`/throw to the slot (LIB-01's `LoadSlot` carries `.failed`). Roots refresh failure must not clear `watchedRoots`.
- **Effort:** S. **Risk:** low.

### LIB-15 Full-library, in-memory sorted song list is re-read on every sort change and revision, LOCAL. Criteria: 5, 1
- **Evidence:** `loadSongs` reads `allTracksDisplay(limit: nil)` (20k `LibraryTrackDisplay`, each with 23 fields, a URL and several Strings) and `applySortOrder` re-reads from SQL with a new ORDER BY on every header click (`LibraryBrowseModel.swift:~330`). The decision (OD-1 full-load, "<100ms selection gate") is documented and measured by `-ASSongsPerf`. Fine at 20k; a 100k library (a plausible "big collector" target) multiplies memory and each reload.
- **Remedy:** Not urgent. Keep OD-1, but make reload incremental via ValueObservation (LIB-01) and consider a `DatabasePool` snapshot-backed paging source if the target library size is raised. Record the target size as a product number.
- **Effort:** M. **Risk:** low. **Depends on:** LIB-01.

### LIB-16 Domain logic and test hooks share the facade file; `async` on non-suspending wrappers; frecency duplicated by id/url, LOCAL. Criteria: 3, 1
- **Evidence:** `LibraryStore.swift` (352 lines) mixes: the facade, 11 verification hooks, the migrator factory, the frecency math (`frecencyAfterPlay`), and two copies of read-modify-write play recording (`incrementPlayCount(url:)` / `(id:)` with 4 near-identical SQL constants). The app's single caller of the URL form is a fallback for queue items with no `trackID` (`+PlayTracking.swift:73`), yet the harness uses it 4 times. `schemaVersion()`, `searchIndexWriteCount()` are `async` for no reason (synchronous reads of a stored property / `Mutex`).
- **Remedy:** Move frecency into its own `Frecency` type/file with the math + the single `recordPlay` SQL (resolve url to id inside the one write); drop the URL overload unless a loose-file queue path appears. Remove `async` where nothing suspends. (Algorithm correctness itself: N27-N29, hand to the panel.)
- **Effort:** S. **Risk:** low.

### LIB-17 Storage/file-system identity edges: `PathNormalizer` and bookmarks, LOCAL. Criteria: 4, 1
- **Evidence:** `PathNormalizer.normalizedString(forPath:)` expands `~`, makes relative paths absolute from `currentDirectoryPath`, `standardizingPath`, NFC. The map notes it has no production test (N41). It runs for EVERY classify/upsert/move (hot path: one `NSString` chain per file; fine) and is the identity key (`tracks.url UNIQUE`). A moved volume (same NAS, new mount name `/Volumes/Music-1`) changes every key: the whole library is "new" and the old rows are swept (LIB-02 again, reduced to the empty-walk guard by the unreachable old path). The root's `bookmark` column is stored but "reserved unused" (`DAO:~104`); `restampRoot` fixes `(dev, inode)` on remount but not the `path`.
- **Remedy:** Treat root identity as `(dev, inode)` + path (the schema has it): on `restampRoot`, detect "same dir at a new path" and update `folders.path` + rewrite track urls by prefix in one transaction (a `relocateRoot` DAO), rather than orphan-and-rescan. Add the PathNormalizer vector tests the map flagged.
- **Effort:** M. **Risk:** med. **Depends on:** LIB-02.

## What is GOOD (keep, copy elsewhere)

1. **Open-path safety design** (`LibraryStore+Open.swift`, `StoreBackup`, `StoreQuarantine`): look first on a read-only connection with checkpoint-on-close disabled, refuse rather than reset, quarantine only on genuine corruption, back up before migrating, typed refusal enum surfaced to the user. This is better than most shipping apps and matches GRDB's `DatabaseMigrator` intent. Copy this pattern for any other persistent store (EQ presets are in UserDefaults).
2. **Facade shape**: `final class LibraryStore: Sendable` over `any DatabaseWriter`, each method one `read`/`write` closure = one transaction, `Database` never escapes, only value types cross. Correct for GRDB 7 / Swift 6 and strictly better than the former actor. The `*Locked(db)` helper convention to compose transactions is clean.
3. **`FolderWalkSchedule`**: a pure value-typed scheduler with its rules written in the header and testable without app/IO. The template for the LIB-06 reducer, and for TransportSnapshot-style logic elsewhere.
4. **Idempotent upsert design**: `ON CONFLICT DO UPDATE ... WHERE <content differs>` so a no-op re-scan writes nothing, proved by a counter; never-lower stamps; additive-only migrations with a gate fingerprint.
5. **Pure kits for decisions** (`LibraryBrowseKit`: `ListSelection`, `GridKeyboardCursor`, `DetailTrackLayout`, `CoalescingWriter`, `PlaylistDialogLatch`): behaviour extracted from SwiftUI into testable value types. The right instinct; the gap is that the loaders (LIB-01) and the activity state (LIB-06) were not extracted the same way.
6. **EXPLAIN-QUERY-PLAN gate** for hot reads (BR5): the plan is asserted index-driven from the same SQL text the read runs. Few apps do this.
7. **Frecency as an O(1) accumulator with an indexable projected rank** (Mozilla Places idea): the read has no `now`, no filesort. Algorithm to the panel but the storage design is sound.

## Algorithms needing a correctness panel (map IDs)

- **N30** `FolderWalkSchedule` (add covers reconcile, cancelled walk owed a reconcile, `removing` set reuse of ids): model-check the transitions, especially `endRemoving` then id reuse while a stale `walkTasks[id]` completes.
- **N36-N40, N44** identity / move-match: cross-root ordering (LIB-03), `LIMIT 2` ambiguity on hard-linked or copied-with-preserved-mtime files (two copies, same dev+inode is impossible for copies but possible for hard links: both rows have the SAME inode and the file size/mtime; ambiguity returns nil and creates a new id: fine; but a hard-link pair where one is deleted is then treated as a move of the other?), inode reuse after delete+create of a different file with the same size and mtime (rare, second-resolution mtime, `mtime` stored in whole seconds), network volumes where inode is unstable.
- **Generation allocation** (`beginScanGeneration`, not a numbered map row): non-unique across concurrent walks (LIB-03).
- **N27-N29** frecency: the `rank = now + (H/ln2) * ln(score)` projection loses precision as `score` grows for a heavily played track? (`score` stays small due to decay; fine) but `incrementPlayCount` uses client time `playedAt` with `max(0, now - lastPlayed)` clamp, so a backwards clock sets rank non-monotonically.
- **N49-N52, N56, N76** album identity/year (LIB-13): `idx_albums_key` includes `folder_key` and `edition_year`; a re-tag that changes a song's year moves it between albums, the old album's `year` is refreshed only in regroup, and FTS album text is `album_title` (title only).
- **N61-N63, N72-N73** search: `ftsMatchQuery` turns any token run into `"tok"*`; CJK has no word boundary so a 1-char prefix query matches broadly (the 2-char gate counts Characters, not tokens).

## Open questions for the founder

1. **Missing vs deleted:** should a file that vanishes from a folder drop out of playlists immediately (today, a design decision recorded as §0.2), or become "missing" for a grace period like Music.app/Navidrome (recommended: tombstone with a 30-day window; it also fixes partial-walk and volume-rename data loss)?
2. **Cross-library search:** unify the three semantics on FTS (recommended: ranked prefix, consistent across tabs; the dead `search()` becomes the Library-wide search the roadmap probably wants) or on the lexical filter (delete the FTS sections)?
3. **Playlist folders:** the DAO, schema (v5) and harness exist, no UI. Ship a UI, or remove the DAO now and leave the tables unused (recommended: remove the DAO, keep the frozen migration)?

5. **Adopt ValueObservation:** a one-model pilot (the Playlists tree is the smallest) to prove it against the break-it suite before converting Songs/Albums?
